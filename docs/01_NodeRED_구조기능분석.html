1 패키지 구조 (모노레포)

Node-RED 최신 버전(v4.x)은 단일 모노레포로 관리되며, packages/node_modules/ 하위에 역할별로 패키지가 분리되어 있다. C# 이식 시 이 경계를 그대로 어셈블리(프로젝트) 분리 기준으로 사용할 수 있다.

2 런타임 핵심 컴포넌트

  • events.js — 런타임 전역 이벤트를 방송하는 싱글턴 EventEmitter
  • comms.js — 에디터 UI와 실시간 통신하는 WebSocket 엔드포인트
  • registry.js — 설치된 노드를 탐색·로딩하는 노드 타입 레지스트리
  • flows.js — 요청된 플로우 설정을 인스턴스화/시작/정지
  • Node.js — 모든 런타임 노드가 상속하는 클래스 프로토타입
  • credentials.js — 자격증명 로드/추가/조회/삭제 API
  • storage/ — 파일시스템 등 플러거블 저장소 시스템

3 노드 생명주기

레지스트리가 노드 타입을 로딩한 뒤, 플로우 배포(deploy) 시 실제 노드 인스턴스가 생성·시작되고, 재배포/종료 시 정리(close)된다.

sequenceDiagram participant Reg as Registry participant Flow as Flow(런타임) participant Node as Node 인스턴스 Reg->>Reg: 설치된 노드 모듈 스캔 Reg->>Reg: node.html + node.js 로딩 Flow->>Reg: 노드 타입 조회 Flow->>Node: new Node(config) Node->>Node: on('input') 리스너 등록 Flow->>Node: start (배선 연결) Node-->>Flow: emit('input', msg) Flow->>Node: close (재배포/정지 시) Node->>Node: on('close') 정리 로직 수행

4 Runtime ↔ Editor 분리 구조

Node-RED는 0.20 버전부터 런타임과 에디터를 명확히 분리했다. 런타임은 헤드리스로 동작 가능하며, 에디터는 Admin HTTP API + WebSocket(comms)를 통해서만 런타임과 통신한다. C# 이식 시에도 Runtime 서비스(백엔드)와 Editor(웹 프론트)를 완전히 분리하는 것을 권장한다.

1 플로우 기반 프로그래밍 모델

Node-RED의 핵심 개념은 4가지다: Node(노드) — 입출력이 정의된 처리 단위, Wire(와이어) — 노드 간 메시지 라우팅 경로, Message(msg) — 노드 사이를 이동하는 JS 객체, Flow(플로우) — 연결된 노드들의 집합(에디터의 탭 하나 = 플로우 하나).

graph LR Inject["Inject 노드
(트리거)"] -- "msg" --> Func["Function 노드
(가공)"] Func -- "msg" --> Switch["Switch 노드
(분기)"] Switch -- "msg (true)" --> Debug1["Debug 노드"] Switch -- "msg (false)" --> HTTP["HTTP Request 노드"] HTTP -- "msg" --> Debug2["Debug 노드"]
개념설명
msg.payload메시지의 주 데이터. 대부분의 노드가 이 필드를 읽고 씀
msg.topic메시지 분류/식별용 필드 (MQTT 등에서 특히 중요)
msg._msgid메시지 추적용 고유 ID (디버그 시 사용)
wires노드 정의(JSON)의 출력 포트별 연결 대상 노드 ID 배열

2 에디터 기능

  • 비주얼 플로우 편집기 — 브라우저 기반 드래그앤드롭 캔버스
  • 팔레트 관리 — 노드 검색/설치/삭제를 레지스트리를 통해 동적 처리
  • Config 노드 — MQTT 브로커 등, 여러 노드가 공유하는 설정을 별도 노드로 분리
  • 서브플로우(Subflow) — 여러 노드를 하나의 재사용 가능한 커스텀 노드로 캡슐화
  • 배포(Deploy) — 편집 중인 플로우를 런타임에 반영 (Full/Modified/Restart 모드)
  • 프로젝트(Projects) — Git 기반 버전관리 연동
  • 디버그 사이드바 — 메시지 payload 실시간 확인
  • Import/Export — 플로우 JSON 클립보드/파일 공유
출처: DeepWiki – Architecture

3 런타임 기능

  • 이벤트 기반 실행 엔진 — 메시지가 노드 사이를 흐르며 처리 트리거
  • Context Storage — Node/Flow/Global 3단계 스코프 데이터 저장 (기본 메모리, 플러그인으로 파일/DB 저장 가능)
  • 보안(adminAuth) — 에디터 접근 인증, 자격증명(credential) 암호화 저장
  • 국제화(i18n) — i18next 기반 다국어 지원
  • 클러스터/멀티프로세스 — 대규모 운영을 위한 확장 구조 지원

4 Admin HTTP API (주요 엔드포인트)

에디터와 커맨드라인 admin 도구가 런타임을 원격 제어하기 위해 사용하는 REST API. C# 포팅 시 ASP.NET Core Controller로 1:1 매핑 가능하다.

Method경로설명
GET/flows전체 활성 플로우 설정 조회
POST/flows플로우 설정 전체 반영(배포). flows.write 권한 필요
GET/flow/:id특정 플로우(탭) 조회
POST/flow단일 플로우 추가
GET/nodes설치된 노드 모듈 목록 조회
POST/nodes새 노드 모듈 설치
GET/settings런타임 설정(버전, 기능 플래그 등) 조회
WS/comms노드 status/debug 메시지 실시간 스트림

5 서브플로우 & 메시지 처리 파이프라인

서브플로우: 여러 노드를 하나의 재사용 노드로 캡슐화. 내부 노드는 자신을 포함한 서브플로우의 Flow Context를 공유하며, $parent. 접두사로 상위 플로우 컨텍스트에 접근 가능하다.

메시지 파이프라인: 입력 노드가 메시지를 생성 → 이벤트로 방출 → 와이어를 따라 다음 노드의 입력 핸들러 호출 → 노드가 처리 후 send()로 재방출, 반복.

sequenceDiagram participant A as Node A participant B as Node B participant C as Node C A->>A: 이벤트 발생 (input/timer) A->>A: send(msg) A->>B: emit('input', msg) via wire B->>B: 처리 로직 실행 B->>C: send(newMsg) via wire C->>C: 처리/종단 (Debug 등)
