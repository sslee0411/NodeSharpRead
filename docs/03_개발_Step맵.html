1 ★ "뼈대 우선, 확장" 개발 순서 철학 (v1.4 신설)

Node-RED 원본은 Inject·Function·Switch·Debug 4개 노드만으로도 "메시지가 흐르는 캔버스"라는 핵심 경험을 완성한다. NodeSharpRead도 이 근본 경험을 가장 먼저 확보해야, 이후에 붙이는 산업용 기능(PLC 구조 설정, Sequence, Dashboard, lssLib 모듈 노드)이 "이미 잘 도는 뼈대 위에 기능을 얹는" 안전한 작업이 된다. 그래서 v1.4부터는 다음 순서를 명시적인 목표로 삼는다.

  1. Stage 1 — 코어 인프라 (Phase 0~4): Contracts→Runtime→Registry→Runner. 아직 화면은 없지만 Editor 없이 dotnet run으로 flows.json을 실행할 수 있는 상태
  2. Stage 2 — Node-RED 뼈대 완성 (Phase 5~8): Editor 뼈대 → 캔버스 → Inject·Switch·Function·Debug 4대 기본 노드 → Editor↔Runner 연동. 이 4개 Phase가 끝나면 "최소 Node-RED 클론"이 완성된다 — 캔버스에서 노드를 배치·연결·배포하면 실제로 메시지가 흐르고, 그 상태가 Editor에 실시간으로 보인다
  3. Stage 3 — 산업용 기능으로 확장 (Phase 9~12): 뼈대가 검증된 뒤에야 구조 설정(PLC/Device Tree) → Sequence → Dashboard → lssLib 모듈 노드화 순으로 NodeSharpRead 고유 기능을 얹는다
  4. Stage 4 — 나머지 Node-RED 기능 보강 + 운영 마감 (Phase 13~14): Catch/Status/Complete, Subflow, Credential, MQTT, MES/ERP 등 부가 노드와 백프레셔·감사로그·배포 패키지 등 운영 안정성 항목
  5. Stage 5 — 향후 로드맵 (Phase 15): OPC-UA, 다중 Runner 관리, 이중화 — 이번 구현 범위 밖, 의도적 보류
🎯 1차 마일스톤 — Phase 0~8 완료 시점에 "Inject → Function → Switch → Debug"가 캔버스에서 배치·연결·배포되고 Runner에서 실행되며 상태가 Editor에 실시간 반영되는 최소 Node-RED 클론이 확보된다. 이 지점부터 산업용 확장(Phase 9~)에 들어간다.

2 ★ 핵심 원칙

  1. 각 Step 완료 후 Clean → Rebuild → 실행 확인(에러 0개) 후에만 다음 Step 진행
  2. 한 Step에 신규 파일 최대 3개 — 그보다 많으면 더 잘게 쪼갠다
  3. Step 완료 기준 = 에러 0개 + 해당 기능이 화면/로그로 동작 확인됨
  4. 이전 Step이 깨지면 현재 Step 중단 → 이전 Step 복구가 최우선
  5. 코드 생성 후 항상 [컴파일 확인 체크리스트] + [사용 설명]을 함께 제공
  6. 각 Step은 02_CSharp_구조설계.html의 몇 번 탭 몇 번 카드를 구현하는지 명시(설계-구현 추적성)
  7. Step 완료 시 이 문서의 ⏳ → ✅ 만 갱신(별도 진행상황 파일을 만들지 않음)
  8. README 개발 지침 5번(단계별 시스템/연동 공백 점검)을 매 Step마다 적용
  9. 세분화 원칙 — 서로 다른 클래스/파일 2개 이상이 묶여 있으면 서브 Step(a/b/c)으로 분할. 목록형 항목(모듈 목록, 위젯 목록, 트리거 종류 등)은 항목 하나당 서브 Step 하나가 원칙(lssLib 11개 모듈 → LL-01~08, Dashboard 위젯 6종 → DB-01a~f 가 이 원칙의 적용 사례)
  10. (v1.4 추가) 뼈대 우선 원칙 — Node-RED 근본 기능(Inject/Function/Switch/Debug, 배포, 실시간 모니터링)은 산업용 확장 기능(구조 설정/Sequence/Dashboard/lssLib)보다 항상 먼저 완성한다. 새로운 요구사항이 생기면 "이게 뼈대에 속하는가, 확장에 속하는가"부터 판단해 Phase를 배치한다
  11. (v1.5 추가) lssLib 포팅 원칙 — NodeSharpRead는 D:\lssLib을 ProjectReference/PackageReference로 직접 참조하지 않는다. 필요한 클래스·함수는 원본과 동일한 구조·시그니처로 NodeSharp.Util 등 NodeSharpRead 자체 프로젝트에 복사(포팅)해 독립 소유한다 — lssLib 원본이 나중에 바뀌어도 NodeSharpRead 쪽 코드는 영향받지 않고, NodeSharpRead만의 사정(예: WPF 전용 최적화)으로 자유롭게 고칠 수 있다. 포팅은 새 설계가 아니라 기계적 복사이므로, 포팅 전용 Step에 한해 "최대 파일 3개" 규칙을 완화 적용할 수 있다(완료 기준은 대신 "원본과 구조·함수 시그니처가 동일한지"로 대체)

3 Step 진행 순서 원칙

  1. Phase 0~4(Contracts→Runtime→Registry→Runner 기반)를 먼저 끝낸다 — Editor 없이도 dotnet run으로 Runner가 가상의 flows.json을 실행할 수 있는 상태를 최우선 목표로 삼는다
  2. Phase 5~8(Editor 뼈대 → 캔버스 → Node-RED 기본 노드 → Editor/Runner 연동)로 "최소 Node-RED 클론"을 완성한다 — Inject/Switch/Function/Debug 4개 노드만으로 캔버스-배포-실행-모니터링 전체 루프가 도는지가 이 Stage의 완료 기준
  3. Phase 9~12(구조 설정 → Sequence → Dashboard → lssLib 모듈 노드화)는 뼈대가 안정된 뒤 순서대로 얹는다 — 구조 설정이 Sequence/Dashboard/lssLib 노드가 참조하는 TagRef의 기반이므로 항상 가장 먼저
  4. Phase 13(나머지 Node-RED 기능 보강 노드)은 Phase 6(캔버스)·Phase 7(기본 노드)이 끝나야 새 노드를 캔버스에서 실제로 붙여볼 수 있으므로 Phase 9~12 이후에 진행해도 무방하지만, Credential(NR-06)처럼 보안과 관련된 항목은 Phase 9(구조 설정에서 TagRef 등 민감 데이터를 다루기 시작하는 시점)와 맞물려 앞당길 수 있다
  5. Phase 14(운영 안정성)는 마지막이 아니라 관련 있는 앞 Phase가 끝날 때마다 조금씩 끼워 넣는다(예: OP-01 감사 로그는 RN-04 헬스체크 직후, OP-15 .gitignore는 Phase 0 직후에 바로)
  6. 서브 Step(a/b/c)이 있는 경우, 같은 Step 안에서는 a→b→c 순서를 반드시 지킨다

3 Phase 7 — Node-RED 기본 뼈대 노드 (v1.4 재배치: Inject·Switch·Function·Debug)

Node-RED가 "Hello World" 수준에서도 보여주는 근본 경험 — Inject로 메시지를 만들고, Function/Switch로 가공·분기하고, Debug로 결과를 확인하는 4단계 루프 — 를 가장 먼저 완성한다. 이전 버전(v1.2·v1.3)에서 이 4개 노드는 Phase 11(기타 Node-RED 기능 보강)에 다른 항목들과 섞여 있었는데, v1.4에서 "뼈대 우선" 원칙에 따라 이 Phase로 앞당겼다. Debug 노드는 설계 문서 전체에서 예시로만 계속 언급되고 실제 구현 Step이 없던 누락이었다(v1.4에서 발견, NR-11로 신설).
